# Run and log a workout

Work from the repository root. Follow `AGENTS.md` for setup status and onboarding. Read `docs/plans-and-sessions.md` and the saved plan for this session. Read an existing checkpoint when resuming. If no approved saved plan exists, use repwerks-plan first. The plan is the immutable baseline, referenced by path and ID in the result. Use a unique session ID and write `sessions/<session-id>.json` at finish or explicit checkpoint. Preferences are not barriers to recording work actually done.

- **Circuit round boundary:** Before prompting the first set of *every* round (including round 1, later rounds, and a resumed round whose first set has not yet been logged), show the full current circuit table. Do this again at each new round even if the exercises and targets have not changed. Include one row per exercise, sets for this round, current targets (reps or duration, load, effort), and results for that exercise from *each* previous round (including skips and changed loads/effort). In round 1, show no previous results. Reflect agreed session-specific target changes. Omit setup instructions and rest from this table. **The table is the prompt for the first set: never add a separate next-action row in the same response.** After each logged set within the round, prompt the next set with only a compact next-action table row (block/round/set, exercise, target/load and any rest); do not echo the logged result. When the next set belongs to a new round, use the full circuit table instead of the compact row. Use prose only for a clarification or change.
- Keep live work in context. Record clear natural-language results without confirmation; an otherwise clear result without a stated status is completed. Parse `12/3` as 12 reps at 3 RIR when RIR is the applicable effort measure, and `12/4 30lb` as 12 reps at 4 RIR with a 30 lb load override. For omitted values, use exact values from the effective prescription (including agreed session-specific changes). Do not invent exact reps from a range: ask for the rep count when omitted. An omitted effort target range may be recorded as that range rather than a single value. Ask briefly when genuinely ambiguous.
- `same` copies reps, effort and load from the most recent completed set of the same exercise and side, then applies any explicit override (for example, `same 27.5lb`). Do not copy status or notes. If there is no comparable completed set, ask. By default, a single result for a unilateral movement applies to both sides unless the user specifies otherwise.
- Track every action in order, including skipped sets and user-performed extra sets or exercises. An explicit report of extra work is enough to record it, even for an unlisted exercise; mark it unplanned and separately ask whether it should enter the approved catalog for future plans. Use repwerks-approve-exercise if the user wants that. Do not block historical logging on approval.
- You may suggest changing future actions; ask before applying a suggested change to the active prescription. A clear user-requested change needs no second confirmation. Keep the original plan intact and represent revised targets as session-specific deviations in the result. Template changes require a separate explicit request and a new saved version through repwerks-plan.
- Correct a reported actual in context (or in the saved checkpoint) rather than adding a duplicate action.
- At user request, checkpoint the full current session as `in_progress` in a single JSON file. On resumption, read it and its referenced plan, reconstruct completed actions, and continue. If context was lost before a checkpoint, explain that unsaved results cannot be recovered.
- At finish, save the full result as `completed`, including work performed even if some planned sets were skipped or never reached. Use `abandoned` only when the user explicitly abandons the workout. Write/update one file per session, not one per set. Distinguish unknown/unperformed planned sets from explicitly skipped ones.
- Save the session's expected and actual duration using `docs/plans-and-sessions.md`. Ask for total duration at finish if not already reported; save completed work even if duration remains unknown. Prefer the user's reported duration over chat elapsed time, and update the same result when duration is supplied later. Preserve the original estimate for comparison.
- If a concrete ambiguity or friction point suggests a simple refinement, briefly flag it after saving the session and ask whether the user wants the workflow changed. Do not interrupt logging, propose speculative optimizations, or modify trainer instructions without approval.
